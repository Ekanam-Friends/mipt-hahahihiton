# Чужие RAG-решения: что берём в навигатор

Разбор от 10 ноября 2026. Источники:
[Danessely/rutube-qa-rag](https://github.com/Danessely/rutube-qa-rag),
[Y1OV/rag4rent](https://github.com/Y1OV/rag4rent),
[Chetoff1228](https://github.com/Chetoff1228?tab=repositories).
Все три автора из команды Ikanam.

## rutube-qa-rag — помощник оператора поддержки (2024)

**Устройство.** Четыре сервиса в docker-compose:
- `embedder`: multilingual-e5-base;
- `neural_worker`: Llama-3.1-8B-Instruct, локально, 8 бит;
- `search_engine`: FastAPI, FAISS и Postgres;
- интерфейсы: Streamlit и Telegram-бот.

**Конвейер запроса** (`search_engine/src/dao.py`, промпты в `config.py`):
1. **Переписывание запроса по истории диалога** (`qr_prompt`). Уточняющий вопрос
   «а если я совместитель?» превращается в самостоятельный запрос.
2. **Фильтр «по теме / мусор»** (`domain_prompt`). Запрос не по теме сразу получает
   шаблонный отказ, LLM-ответ не генерируется.
3. Поиск top-10 по FAISS.
4. **Map-reduce.** Каждый фрагмент LLM проверяет отдельно и параллельно: «есть ли тут
   ответ». Если нет, возвращает `!не релевантный фрагмент!`. Затем из выживших фрагментов
   собирается итоговый ответ.
5. Все ответы LLM приходят строго в JSON (`{"answer": ...}`). Если JSON сломан, есть запасной
   путь.
6. Оценка поиска по acc@3, acc@5 и acc@10 на тестовом наборе (`acc_testing`).

**Что берём:**
- Переписывание запроса нужно для уточняющих вопросов, это одна из наших четырёх фишек.
- Фильтр «вне темы» до поиска даёт дешёвый ранний отказ.
- Map-шаг как **проверка релевантности каждого фрагмента** — готовый механизм для честного
  отказа: если ни один фрагмент не выжил, регламента нет. Ещё он отбирает цитаты: в чек-лист
  попадают только фрагменты, прошедшие проверку.
- JSON-контракт и запасной путь. Нам нужна схема богаче: шаги, ответственный, срок,
  документ, пункт, цитата.
- acc@k для оценки поиска, плюс наша метрика «ответил / честно отказал».

**Что не берём:** локальные Llama и e5 на torch. Для них нужна GPU, а образ собирается
долго.

## rag4rent — подбор загородных домов (2024)

**Устройство.** LangChain, FAISS, эмбеддинги multilingual-e5-large-instruct и
**GigaChat-20B-A3B-instruct локально через vLLM**. Интерфейс на Streamlit.

**Что берём:**
- **GigaChat-20B-A3B-instruct**: открытые веса, запуск через vLLM. Это конкретная модель
  для задела «развернуть внутри контура МФТИ». Получается то же семейство GigaChat, что в
  демо через API, только документы не покидают периметр. Архитектура MoE: всего 20B
  параметров, активны около 3B, поэтому инференс относительно дешёвый. Авторы запускали
  её на двух GPU.
- Структурированный системный промпт (инструкции, запреты, цепочка рассуждений) — хороший
  каркас для промпта чек-листа.

**Что делаем наоборот:** их промпт прямо запрещает отвечать «подходящих вариантов нет» и
требует всегда что-то предложить. Для подбора домов это нормально, для регламентов это
провал. У нас отказ — это обязательное поведение, которое мы показываем на демо.

## Chetoff1228

Готового RAG-репозитория нет. Полезное по соседству:
- `LLMevalFM` — бенчмарк фактической точности LLM на русском. Подход пригодится для нашего
  набора контрольных вопросов.
- `NLP-2026/lesson-04-gpt` — семинар про генерацию и RAG на transformers.
- `information_search` — поисковая задача Тинькофф с собственными метриками.

## Итог: что меняется в плане

| Шаг конвейера | Источник |
|---------------|----------|
| Переписывание запроса по истории (для уточнений) | rutube-qa-rag |
| Фильтр «вне темы» → ранний отказ | rutube-qa-rag |
| Гибридный поиск (BM25 + эмбеддинги) по пунктам | наше |
| Проверка каждого фрагмента на релевантность (map) → отказ, если ни один не прошёл | rutube-qa-rag |
| Генерация чек-листа в JSON с цитатами | rutube-qa-rag (JSON) + наше (схема) |
| Проверка, что цитата дословно есть в документе | наше |
| Оценка: acc@k поиска + доля верных отказов | rutube-qa-rag + наше |
| On-prem: GigaChat-20B-A3B-instruct через vLLM | rag4rent |
