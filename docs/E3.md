# E3 — проверяемый ответ и порядок действий

Работа ведётся на официальном снимке 20 файлов, загруженном 11.11.2026. Изменения кода и успешные unit-тесты сами по себе не означают приёмку качества ответов. Итоговые результаты и ограничения приведены в конце этого документа.

## Контракт ответа

`Navigator.ask()` возвращает один из пяти статусов:

| Статус | Значение |
|---|---|
| `answer` | Краткий ответ и, для процедуры, шаги прошли проверки по доступным источникам |
| `partial` | Есть подтверждённая часть; пробелы перечислены в `missing_information` |
| `clarify` | Требуется роль/дата/редакция, либо выявлено расхождение |
| `not_found` | В доступном снимке поиск или проверка не нашли подтверждённого ответа; это не доказательство отсутствия нормы вообще |
| `error` | Ошибка индекса, провайдера, JSON, доказательств или лимита контекста; это не отсутствие регламента |

`summary` — список кратких выводов `text` с `evidence`. `steps` содержит `action`, `responsible`, `deadline`, `documents` и доказательства. `kind=fact` запрещает шаги. У доказательства есть настоящий `chunk_id`, полный исходный текст фрагмента, название документа, пункт/ячейки, URL и `view_path` с точным якорем. Ссылки и названия берутся из индекса, а не из текста модели. Сохранены прежние поля шага `quote`, `chunk_id`, `ref`, `url` для совместимости; новый интерфейс должен отображать все `evidence`.

`sources` перечисляет использованные документы и документы, по которым показаны замечания о применимости. Источники содержат SHA-256 и дату загрузки; `corpus_snapshot` сохраняет даты загрузки снимка даже при отказе. Они не являются датами вступления норм в силу. Для XLSX отдельно показаны формулы без сохранённых результатов и примеры адресов; приложение не вычисляет их молча.

## Проверки

1. Поиск E2 сохраняет кандидатов для каждой части вопроса и доказательства применимости. При явном запросе полного порядка дополнительно подгружаются все соседние пункты найденного раздела. Это не доказательство, что другие разделы не применимы.
2. В режиме по умолчанию `source_preserving=True` модель получает недоверенные источники как JSON с идентификаторами исходного текста. Для справочного вопроса это цельные предложения; для процедуры — полные исходные пункты, чтобы действие не теряло срок или условие из следующего предложения. JSON Schema разрешает выбирать только существующие ID. Модель выбирает относящиеся к вопросу пункты и их порядок, а программа переносит текст без перефразирования. Если пользователь явно задал полный диапазон пунктов, код требует каждый пункт ровно один раз: пропуск блокируется независимо от положительного вердикта модели. Подстроки, многоточия и свободный текст для фактических утверждений не принимаются. Полный исходный пункт прикладывается как цитата. Сроки, исполнители и документы остаются внутри исходной формулировки действия; отдельные поля могут быть пустыми и не заполняются догадками. Это отличается от baseline без модели, который просто выдаёт первые пять выдержек и всегда остаётся частичным.
3. Проверяются структура, типы, лимиты, наличие источника и непрерывность цитаты в соответствующем фрагменте. Переназначения на другой источник и вырезания условий многоточиями нет.
4. Отдельный вызов модели проверяет смысл каждого краткого вывода и отдельно действие, ответственного, срок и каждый документ каждого шага. Он также проверяет пропуски, порядок и обоснованность отказа/уточнения. Для открытой процедуры сначала проверяется прямая применимость каждого найденного пункта к каждой отдельной части вопроса: один пункт и одна часть на вызов. Тематическая близость, заголовки и функции подразделений не считаются действиями. Все признанные относящимися пункты сохраняются; отдельный вызов может только упорядочить их перестановкой без удаления. Затем каждая часть проверяется отдельно, причём каждый такой проверяющий видит весь найденный контекст, включая невыбранные пункты. Исходы частей объединяются с сохранением пробелов; ответ на первую часть не подменяет вторую. Общий префикс источников позволяет локальному серверу переиспользовать KV-кэш.
5. Неподтверждённый шаг исключается целиком, чтобы удаление срока или условия не исказило смысл. Ответ становится частичным. Если отвергнуты все краткие выводы, возвращается ошибка проверки. При неподтверждённой последовательности шаги не показываются. Конфликт должен иметь доказательства с обеих сторон.
6. Некорректный JSON, неполная проверка полей, переполнение и отказ проверяющего блокируют выдачу черновика. Автоматической подмены отказавшей модели извлекающим режимом нет. Явный извлекающий режим возвращает `partial` с выдержками и сообщает, что полнота и порядок не проверены.

Проверяющий использует **ту же локальную модель в отдельном вызове**. Это дополнительный фильтр, а не независимый эксперт и не математическое доказательство следования. Коррелированные ошибки возможны. При ручной сверке свободного перефразирования выявлен конкретный ложноположительный вердикт: модель перенесла формы 0504512/0504515 с Решения о командировании на Приказ, а второй вызов подтвердил текст. Опыт сохранён в `data/official/e3-paraphrase-baseline-report.json` с отклонённой сверкой. Поэтому свободное перефразирование по умолчанию отключено; параметр `source_preserving=False` оставлен только для исследования и не принят по качеству. Дословное сохранение исходных предложений устраняет такой перенос при переформулировании, но не доказывает релевантность, полноту, правильность порядка или применимость выбранных норм. Поэтому приёмка включает просмотр ответов и оригинальных фрагментов; успешное самоутверждение модели не считается достаточным.

Инструкции внутри источников, вопроса, истории и черновика объявлены недоверенными. Генератор не получает инструментов, секретов или возможности исполнять код. JSON Schema, разрешение ID и проверки доказательств дополняют системную инструкцию; устойчивость к произвольным атакам этим не гарантируется.

## Воспроизведение

```powershell
# Runtime и модель; неизменяемые версии и SHA-256 проверяются установщиком
.\scripts\setup_local_model.ps1
# Сервер в отдельном терминале, остановка Ctrl+C
.\scripts\start_local_model.ps1

$env:REGNAV_LLM='openai'
$env:OPENAI_BASE_URL='http://127.0.0.1:8087/v1'
$env:OPENAI_API_KEY='EMPTY'
$env:OPENAI_MODEL='regnav-local'
$env:REGNAV_LLM_TIMEOUT='1800'
$env:REGNAV_MAX_TOKENS='1800'
.venv\Scripts\python.exe -X utf8 -m regnav --data data/official ask 'Какие официальные каналы подачи обращений в первую линию техподдержки УИТ?' --json --as-of 2026-11-12

# Все 26 вопросов E2 с настоящей генерацией
.venv\Scripts\python.exe -X utf8 scripts/verify_e3.py
# Дополнительные полные процедуры, частичный ответ и негативные вопросы
.venv\Scripts\python.exe -X utf8 scripts/verify_e3.py --questions eval/e3-questions.jsonl --output data/official/e3-extra-report.json
# Возобновление прерванного сбора допустимо только при совпадении хешей кода, модели и эталонов
.venv\Scripts\python.exe -X utf8 scripts/verify_e3.py --resume
.venv\Scripts\python.exe -X utf8 -m pytest -q
```

Ранее для проверки использовалась [Qwen3-1.7B](https://huggingface.co/Qwen/Qwen3-1.7B), [GGUF автора квантования](https://huggingface.co/bartowski/Qwen_Qwen3-1.7B-GGUF/tree/dcb19155b962dbb6389f4691a982043a8e651022), Q4_K_M, 1 282 439 584 байта, SHA-256 `72c5c3cb38fa32d5256e2fe30d03e7a64c6c79e668ad84057e3bd66e250b24fb`. Сервер: llama.cpp b12284, только `127.0.0.1:8087`, CPU, 8192 токена, один слот, бюджет reasoning 0. Исторический baseline E0 доступен через `setup_local_model.ps1 -Baseline` и `start_local_model.ps1 -Baseline`. Файл `.env.example` не загружается автоматически.

В раннем опыте Qwen3-4B-Instruct-2507 при доступных около 2,1 ГБ из физических 7,8 ГБ RAM обработка входа замедлялась до 11–20 токенов/с; опыт остановили до получения ответа. Причина замедления по одной задержке не установлена, счётчики подкачки не снимались. Этот ранний опыт сохранён отдельно и не даёт оценки качества. При возобновлении пользователь разрешил длительный прогон: текущий профиль 4B с контекстом 12288 и KV-кэшем q4_0 используется по умолчанию; `-Large` оставлен как совместимый псевдоним, `-Small` выбирает 1.7B. Фактические задержки текущих ответов записываются в отчёты.

## Приёмочные материалы

- `eval/e2-questions.jsonl`: прежние 26 эталонов поиска, теперь с фактическими ответами. Их `required_elements` не являются полноценной разметкой всех процедур.
- `eval/e3-questions.jsonl`: дополнительные сценарии с ожидаемыми статусами и обязательными элементами процедур.
- `scripts/verify_e3.py`: проверяет хеши оригиналов, сохраняет реальные запросы/ответы модели, ответы конвейера, длительность, попадание эталонных фрагментов и состояние последующей сверки. В отчёте фиксируются хеши модели, кода и набора вопросов. Ключей API в отчёте нет.
- `tests/test_e3.py`: проверки полей и статусов, отклонение неверных ссылок/цитат, ошибок проверяющего, пропусков и неправильного порядка; источник с инструкцией проверен на уровне передачи недоверенных данных, а не как доказательство устойчивости живой модели.
- `data/official/e3-baseline-report.json` и `e3-pilot-report.json`: сохранённые неуспешные опыты с Qwen2.5-1.5B; они не являются финальным результатом.

Отчёт сбора первоначально содержит `quality_acceptance=false` и `source_review.state=pending`. Сбор ответов и попадание нужной цитаты не равны приёмке. Для каждого сценария требуется сверить смысл, обязательные элементы, условия, порядок и применимость с оригиналами. Рецензент и основания решения должны быть сохранены явно; проверка Codex не должна называться приёмкой человеком или владельцем регламентов.

Все части составного вопроса проверяются отдельно, в том числе если одна из них просит процедуру; отсутствие сведений по второй части сохраняется как пробел. Подтверждённая справочная часть не превращается в шаги неподтверждённой процедуры.
- В живом промежуточном прогоне обнаружены и отклонены: ошибочный статус `answer` для поддержки вместе с неподтверждённой ипотекой; `error` вместо обоснованного `not_found` для пароля. Для проверки отказа уточнено различие между полнотой фактического ответа и обоснованностью `not_found`; повторные ответы проверяются заново, старые вердикты не объявляются успешными.
- Ручная сверка отклонила ещё два положительных самоутверждения модели: лишние шаги и пропущенный максимум 1 год в общем вопросе ЦОД/поддержки; пропущенный п. 3.2 о контактах в подборе персонала. Ответы и причины сохранены в `data/official/e3-rejected-procedure-baseline-report.json`. Для процедур введён выбор целых пунктов, а для явно заданного диапазона — обязательная полнота набора ID и проверка перестановки. Это исправления по найденным дефектам; успешность повторных живых ответов оценивается отдельно.
- Большой совместный выбор целых пунктов тоже не принят: в `e3-before-relevance-report.json` многодокументный ответ остался частичным, с лишними определениями и ошибочно отброшенной поддержкой. Поэтому открытые процедуры переведены на отдельную проверку применимости каждого пункта и проверку каждой части вопроса. В `e3-relevance-pilot-report.json` сохранены 7/7 ожидаемых решений на малом диагностическом наборе (включая отрицательные заголовок, определение, функции и общую ответственность). Это набор настройки, а не независимая оценка качества. Полный прогон текущего конвейера выполняется отдельно.

Текущие приёмочные ответы записываются в `data/official/e3-current-answer-report.json` и `data/official/e3-current-extra-report.json`; отдельная сверка Codex — в `eval/e3-final-source-reviews.json`. Предыдущие `e3-final-*` — промежуточные опыты с сохранёнными ошибками и более ранними хешами. До завершения обоих наборов и сверки всех ответов E3 остаётся непринятым.

### Журнал повторных проверок

[Реестр прогонов и сценариев](E3-test-log.md) содержит успешные и неуспешные опыты. Полный stdout, stderr, exit code и хеши проверенных файлов новых unit-прогонов сохраняются в `data/official/e3-unit-runs/`; более ранние наблюдения отделены от этих записей и не получают выдуманных хешей или времени запуска. Модельные отчёты сохраняют входы и ответы всех вызовов. Рецензии привязаны к SHA-256 конкретного итогового ответа.

При повторной сверке основного набора выявлены ещё два ложноположительных результата самооценки: дата новой редакции вместо явно запрошенного старого приказа 460-1 и ответственность отправителя вместо адресата карточки в составном вопросе. Эталонная цитата могла присутствовать в метаданных или в том же пункте и не гарантировала правильности краткого ответа. Сохранённый исход — `e3-before-fact-relevance-report.json`; последующий ошибочный составной ответ также отклонён в рецензиях. Контекст вопроса о начале действия ограничен явно указанным приказом; выбор нескольких справочных предложений дополнен проверкой их прямой уместности. При использовании разных неподтверждённых редакций итог требует уточнения. Справочные части составного вопроса теперь изолируются и в самом payload выбора, чтобы полный вопрос не перетягивал выбор на другую часть.

Дополнительные 7 сценариев сверены с оригиналами и приняты технической сверкой Codex в `e3-current-extra-report.json`. Их реальные локальные вызовы хранятся в неизменяемом `e3-procedure-inference-report.json`. После изменений постобработки сохранённые вызовы воспроизводятся только при побайтовом совпадении промптов; отчёт явно сохраняет режим replay, исходные хеши и длительность настоящего вывода. Это не новый живой прогон и не оценка неизвестных вопросов. Ошибка регистратора при несовпадающем порядке вопросов остановила первый replay, не обойдя проверку промптов; незавершённый исход сохранён в `e3-replay-order-failed-report.json`, порядок очереди исправлен и покрыт регрессией.

Повтор после одной лишь изоляции частей тоже отклонён: `e3-isolation-only-failed-report.json` вновь содержит ответственность отправителя вместо адресата. Проверка уместности раньше включалась только при выборе нескольких предложений и пропускала ошибочный единственный выбор. Теперь она выполняется для каждого выбранного справочного предложения. Если все выбранные предложения отклонены, разрешён один повторный выбор из остальных ID с обязательной повторной проверкой. Возврат отклонённого ID блокируется кодом; повторная нерелевантность даёт пробел, а не автоматическое подтверждение. Три регрессионных случая проверяют исправленный выбор, исчерпание попытки и недопустимый возврат отклонённого ID. Новый полный живой прогон основного набора начат заново; прежние рецензии применяются только при совпадении хеша ответа. Изменение кода после предыдущей сверки семи дополнительных сценариев также требует их повторной проверки для текущего снимка реализации.

Сверка ответа о финансовой структуре выявила утечку метаданных поиска: к корректным положениям 3614-1 добавлялось предупреждение о незаполненной дате из постороннего регламента командировок. Постобработка теперь оставляет применимость и предупреждения использованных документов и связанных редакций; одинаковые предупреждения объединяются. Связанный конфликт редакций сохраняется, даже если одна сторона не вошла в краткий ответ. Регрессия отдельно проверяет удаление чужого предупреждения, сохранение предупреждения с совпадающим текстом для собственного источника и сохранение связанной старой редакции. Это изменение выполняется после всех вызовов модели; сохранённые вызовы основного прогона будут воспроизведены через новую постобработку с проверкой точного совпадения промптов.

В `travel-paraphrase` проверяющий отверг одно лишнее утверждение; два оставшихся покрывают вопрос по п.46, однако конвейер консервативно поставил `partial`, поскольку исходная полнота оценивалась до удаления. Статус вручную не повышается. Для справочного ответа после частичного удаления введён один новый вызов проверки уже очищенного набора с доступом ко всему исходному контексту: полнота подтверждается заново, а при реальном пробеле сохраняется `partial`. Повторное отклонение всех оставшихся утверждений блокирует ответ. Три регрессии проверяют каждый исход. Процедуры не переводятся в полный ответ по этому правилу.

Живой повтор `travel-paraphrase` подтвердил исправление: исходные флаги `[true, true, false]`, одно удаление, новый вызов проверки, итоговые `[true, true]`, `complete=true`, статус `answer`. Обе сохранённые формулировки сверены с п.46 оригинальной страницы 12. Длительность нового полного ответа — 282,03 с; это наблюдение данного запуска, не изолированный бенчмарк.

При `borrowing` выявлена двусмысленность эталонного вопроса: «Какой приказ отменяет 5990-1…» допускает обратное направление отмены, тогда как ожидаемые данные относятся к приказу 1465-1, отменённому самим 5990-1. Это сверено непосредственно с первой страницей оригинального PDF: п.1 отменяет 1465-1, п.2 вводит Регламент с даты подписания, дата в шапке — 03.11.2026. Вопрос уточнён до двух явно сформулированных частей; количество вопросов, ожидаемые данные и исходные фрагменты сохранены. Исправление с хешами до/после записано в `eval/e3-question-corrections.json`. Неуспешный исход двусмысленной формулировки сохраняется; уточнённый сценарий требует отдельного живого повторного прогона. Остальные ответы переносятся только при совпадении их вопроса, эталонов и реальных модельных промптов.

Во время unit-проверок параллельно появились изменения E4 в `regnav/web` и `tests/test_web.py`. Общий прогон дал 99 успешных тестов. Широкий регистратор выставил флаг нестабильного общего снимка: до/после различались `regnav/web/accounts.py` и `tests/test_web.py`, затем изменился `regnav/web/app.py`. Это не падение тестов и не основание отклонять E3: его ядро, CLI и собственные тесты в этом прогоне не менялись, результаты поднабора E3 засчитаны. Исходный флаг регистратора сохранён с уточнением охвата. Файлы E4 остаются в работе владельца изменений. Регистратор E3 теперь явно запускает `test_core`, `test_ingest`, `test_e2`, `test_e3`, `test_e3_acceptance`; отдельный прогон 94 тестов прошёл со стабильным снимком E3. Сохраняются хеши до и после, список отличий и оба exit code — pytest и регистратора.
